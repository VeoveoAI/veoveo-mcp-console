# Console Design

This document is the design and operational contract for the `veoveo-mcp-console`
crate, the Hub MCP server.

The console is the MCP provider of the Hub's activities for agents. It holds no
authority of its own: each tool calls the Hub as the calling user, and the Hub
decides. Agents reach it on their Hub connection as `console__{tool}`.

## Service Identity

```text
crate        veoveo-mcp-console
binary       veoveo-mcp-console
repository   veoveo-mcp-console
slug         console
URI scheme   console
permissions  console.use
MCP          /console/mcp
liveness     /livez
readiness    /readyz
port         8805
```

`veoveo_mcp_console::SLUG` holds the slug once. The permission `console.use`, its
resource type `console.activity`, the scope, the URI scheme, the documents and the
default key directory `/var/lib/veoveo/console/keys` derive from it.

## Standards And Protocols

| Standard or protocol | Implemented profile |
|---|---|
| [Model Context Protocol](https://modelcontextprotocol.io/specification/) | Version `2026-07-28`, JSON-RPC 2.0 over Streamable HTTP, under the hosted MCP contract `https://veoveo.ai/contracts/hosted-mcp` that `veoveo-hub-sdk` implements. Tools with typed structured content, and the host's documents and contract resources. No prompts, Tasks or subscriptions. |
| [JSON Schema Draft 2020-12](https://json-schema.org/draft/2020-12/) | Tool inputs and results, generated by Schemars from the contract's types. |
| [JWT access tokens RFC 9068](https://www.rfc-editor.org/rfc/rfc9068.html) | The Hub forwards each request with an access token that names the caller, the caller's tenant and the permissions it granted. |
| [Veoveo server registration](https://github.com/VeoveoAI/veoveo-hub-sdk) | The server initially registers through RFC 7591, resumes native RFC 7592 credentials on restart, and declares its permission in `ai.veoveo/authorization`. |

## Domain Contract

The console answers these questions for an agent, as its user:

- Why does this branch of a repository serve, or not?
- What did its sandbox write, and which of its network requests were denied?
- Which branch's instance serves me each server?
- Which repositories does the Hub build and serve for me?
- Where do I push a new repository of my own?
- Who can reach my repository, and how do I share it with a person or a group?
- Is my Computer current, what does an update bring, and will you restart it?

| Tool | Hub route | Result |
|---|---|---|
| `status(repository, branch, wait?)` | `GET /factory/{profile}/instance?repository=&branch=&wait=` | `InstanceStatus`: deployment, workspace, sandbox name and ID, OpenShell's phase, exit code, restart count and conditions, the applied and serving revision, the Hub's last failure and any warning |
| `logs(repository, branch, since?, limit?)` | `status` without waiting, then the log store | `Logs`: the sandbox's name and ID and its latest lines, oldest first, each with its time, its source (`stdout`, `stderr` or `denied`) and its text, and whether older lines were left out |
| `select(server, branch \| null)` | `PUT /selection/{profile}/{server}` with `{"branch": …}`; `DELETE` when the branch is null | `Selection`: the server and its selected branch |
| `watch(repository)` | `PUT /factory/{profile}/watch?repository=` | `Watching`: the repository |
| `create_repository(name, id?)` | `POST /lore/{profile}/repositories` with `{"name": …}` and the optional `"id"` | `Repository`: its ID, name and clone `remote`, `<Lore remote>/<id>` |
| `repository_access(repository)` | `GET /lore/{profile}/repositories/{id}/access` | `RepositoryAccess`: the repository and each person, by email and name, and group, by name, that may reach it, with its level, `member` or `owner` |
| `share_repository(repository, person \| group, access)` | `PUT /lore/{profile}/repositories/{id}/access` with `{"person": …}` or `{"group": …}` and `{"access": …}`, one of `member`, `owner` or `none` | `RepositoryAccess` after the change |
| `groups()` | `GET /lore/{profile}/groups` | `Groups`: each group the caller belongs to, with its ID, its members by email and name and their roles |
| `create_group(name)` | `POST /lore/{profile}/groups` with `{"name": …}` | `Group`: its ID and name, with the caller as its owner |
| `set_group_member(group, person, role)` | `PUT /lore/{profile}/groups/{name}/members` with `{"person": …, "role": …}`, one of `member`, `owner` or `none` | `Group` after the change |
| `computer(restart?)` | `GET /computer/status`; with `restart: true`, `POST /computer/restart` | `ComputerStatus`: the version the caller's Computer runs and the current one, whether an update is available and what it brings, a restart that runs or the last one's failure, a blocking cause, and an update installed since the caller was last told |

Every tool requires `console.use`. `{profile}` is the profile the caller reached the
console through, as the forwarded identity names it. `wait` is capped at 60 seconds,
as the Hub caps it; absent, it is 0.

### Calls To The Hub

The route builder declares `calls_hub`, so the server registers the token exchange
grant without declaring uses of any other server. Each tool takes the bearer
`ctx.client()?.hub_bearer()` returns: the caller's forwarded token exchanged at the
Hub's token endpoint for the caller's profile, naming no permissions, cached for the
request. The Hub admits it as the caller and decides each route by the caller's own
grants: a selection is the caller's own, an instance's status and a watch need the
caller's grant on the repository, a creation needs the caller's tenant, and a share or a
membership needs the caller to own the repository or the group. A Hub
refusal, such as 403 without a grant or 404 without an instance, is the tool's error
result, naming what was refused, the HTTP status and the Hub's RFC 9457 title and
detail, and the problem's `id` extension when it has one. Path segments are
percent-encoded one by one.

`create_repository` is one Hub call: the Hub creates the repository in its Lore
deployment as the caller, publishes the revision that registers it and assigns the
caller its owner, and answers once that revision is active, so the caller's first push
is admitted. A name Lore holds already is 409. A
503 that names an `id` is a repository Lore created but the Hub did not register;
calling again with the same name and that `id` registers it, and nobody but its
creator can. The call waits up to 120 seconds, since giving up earlier would lose the
created `id`.

`share_repository` and `set_group_member` name a person by the email they sign in with
and a group by its name; one argument of `person` and `group` is required. Only an owner
shares, and the Hub refuses a change that would leave the caller without `owner`, so the
error says so. A person who has never signed in cannot be named yet. Access through a
group follows its members: adding someone to a group gives them every repository shared
with it, within the Lore token lifetime. A group is the same group to every server: a
server that grants to groups, such as Artifact, names it by the ID `groups` answers, and a
member holds that grant from their next call.

`InstanceStatus` follows the Hub's answer and reads only the fields it names; a phase
or stage it does not know fails the call with the Hub's value.

### The Computer Tool

`computer` reports the caller's own Computer; the Hub finds it by the caller's tenant
and principal. Its paths name no profile: the Hub admits the exchanged token for its
one Computers profile, so the tool serves callers who reach console through that
profile, as agents in a Computer do; another profile's caller gets the Hub's 401. A restart is the Hub's: it answers `202` with the status at once and
deletes the sandbox only a few seconds later, so an agent restarting its own Computer
receives the answer before its session ends. The tool's argument tells agents to
restart only when the person asks.

A tool list is shared by every caller, so the description names only the current
version and its summary, and the call says whether the caller's Computer is behind.
Console reads the current version from the Hub's public `GET /computer/version`, with
no credentials, at start and about every 30 seconds. When the version changes it sets
the description through the SDK's `ToolDescriptions`, which serves it in `tools/list`
and sends `notifications/tools/list_changed` on every listen the Hub holds, so the
Hub refreshes its catalog and tells its clients. Until the first answer the
description names no version; a failed read keeps the last one. The description tells
agents: "Call this at the start of a session; if an update is available or was just
installed, tell the person what's new in a line or two; restart only when the person
asks."

### Logs

Everything a sandbox's main program writes — the Lore sync, the build and the server
— is the output of its workload pod's container `agent`. Vector ships every
container's output to the installation's VictoriaLogs with the pod's labels as
`kubernetes.pod_labels.*` fields. The workload pod and its supervisor pod both carry
the sandbox's OpenShell ID as `openshell.ai/boundary-pair`, and the supervisor writes
OpenShell's network events as OCSF lines whose action is ` DENIED ` for a refusal.

`logs` first reads the instance's status from the Hub without waiting, as the caller:
the Hub's answer is the access check, and it names `sandboxId`. Without a sandbox it
returns no lines. Otherwise it sends one LogsQL query to `/select/logsql/query`:

```text
"kubernetes.pod_labels.openshell.ai/boundary-pair":="<sandboxId>"
  (kubernetes.container_name:="agent"
   or ("kubernetes.pod_labels.openshell.ai/boundary-role":="supervisor" OCSF DENIED))
  | sort by (_time desc) limit <limit + 1>
  | fields _time, _msg, stream, "kubernetes.pod_labels.openshell.ai/boundary-role"
```

with `start` set to `since` when given. Values are LogsQL quoted strings. A supervisor
record is a `denied` line; the others are `stdout` or `stderr` by Vector's `stream`.
The latest `limit` lines (200 by default, at most 1000) return oldest first, each cut
to 4096 bytes; the extra record sets `truncated`. A refusal of the log store is the
tool's error with its status and up to 512 bytes of its text. The log store needs no
credentials.

Measured on 2026-10-22 against `victoriametrics/victoria-logs:v1.53.0` (the
installation's digest) in a disposable container, with seven synthetic records shaped
like Vector's events: the query returned exactly the sandbox's four `agent` lines on
stdout and stderr and its supervisor's one `DENIED` line, newest first, and left out
its supervisor's `ALLOWED` line and another sandbox's output and denial; `limit 2`
returned the two newest; `start=2026-10-22T10:00:03Z` was inclusive; a malformed
query answered 400 with VictoriaLogs' parse error. Not measured: the records Vector
writes from a live sandbox.

The log store answers whoever reaches it, so reaching it is the boundary. The console
is a platform component: it runs as the sandbox `console` in the installation's
`vv-services` workspace, registered on the namespace path, and only its policy admits
the log store. A console branch can still be served as a factory instance, but its
`logs` fails there: the factory base policy withholds the log store, and a repository
policy that added it would let any branch read every instance's output.

## Architecture

### Library Features

| Feature | Holds | Depends on |
|---|---|---|
| `contract` | `ConsolePermission`, `ConsoleScope`, `ConsoleProvider` and the tools' requests and results | `veoveo-types`, the SDK's `contract` feature, Serde and Schemars |
| `server` (default) | The hosted server and the binary | The SDK's `server` feature, core's store, reqwest and rmcp |

The `contract` feature also depends on chrono for the times of `logs`.

### Modules

| Module | Responsibility |
|---|---|
| `contract` | The public types a consumer compiles against |
| `mcp` | The typed ready routes, checked setup, registration declaration, the Hub's routes (`mcp::hub`), the log store (`mcp::logs`) and the `computer` description that follows the current version (`mcp::computer`) |
| `server` | Configuration, registration with the Hub, the database connection, the process instance and serving |

### Startup

The server builds its registration declaration from the public base URL and checks the
MCP setup before it contacts anything. It registers with the Hub, which issues a
database login for the `console` schema and the trust for forwarded tokens. With that
login it holds a process instance and serves. Serving ends on SIGTERM, on Ctrl-C or
when the instance loses its lock. Native saved registration remains for resume.

## Persistence

None. The server keeps no tables. Its database connection holds the kernel process
instance whose liveness the Hub reads as the server's health.
