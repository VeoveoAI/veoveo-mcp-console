# Console Design

This document is the design and operational contract for the `veoveo-mcp-console`
crate, the Hub MCP server.

The console is the MCP provider of the Hub's activities for agents. It holds no
authority of its own: each tool calls the Hub as the calling user, and the Hub
decides. Agents reach it on their Hub connection as `console__{tool}`.

## Service Identity

```text
crate        veoveo-mcp-console
binary       veoveo-mcp-console
repository   veoveo-mcp-console
slug         console
URI scheme   console
permissions  console.use
MCP          /console/mcp
liveness     /livez
readiness    /readyz
port         8805
```

`veoveo_mcp_console::SLUG` holds the slug once. The permission `console.use`, its
resource type `console.activity`, the scope, the URI scheme, the documents and the
default key directory `/var/lib/veoveo/console/keys` derive from it.

## Standards And Protocols

| Standard or protocol | Implemented profile |
|---|---|
| [Model Context Protocol](https://modelcontextprotocol.io/specification/) | Version `2026-07-28`, JSON-RPC 2.0 over Streamable HTTP, under the hosted MCP contract `https://veoveo.ai/contracts/hosted-mcp` that `veoveo-hub-sdk` implements. Tools with typed structured content, and the host's documents and contract resources. No prompts, Tasks or subscriptions. |
| [JSON Schema Draft 2020-12](https://json-schema.org/draft/2020-12/) | Tool inputs and results, generated by Schemars from the contract's types. |
| [JWT access tokens RFC 9068](https://www.rfc-editor.org/rfc/rfc9068.html) | The Hub forwards each request with an access token that names the caller, the caller's tenant and the permissions it granted. |
| [Veoveo server registration](https://github.com/VeoveoAI/veoveo-hub-sdk) | The server initially registers through RFC 7591, resumes native RFC 7592 credentials on restart, and declares its permission in `ai.veoveo/authorization`. |

## Domain Contract

The console answers these questions for an agent, as its user:

- Why does this branch of a repository serve, or not?
- Which branch's instance serves me each server?
- Which repositories does the Hub build and serve for me?

| Tool | Hub route | Result |
|---|---|---|
| `status(repository, branch, wait?)` | `GET /factory/{profile}/instance?repository=&branch=&wait=` | `InstanceStatus`: deployment, workspace, sandbox name and ID, OpenShell's phase, exit code, restart count and conditions, the applied and serving revision, the Hub's last failure and any warning |
| `select(server, branch \| null)` | `PUT /selection/{profile}/{server}` with `{"branch": …}`; `DELETE` when the branch is null | `Selection`: the server and its selected branch |
| `watch(repository)` | `PUT /factory/{profile}/watch?repository=` | `Watching`: the repository |

Every tool requires `console.use`. `{profile}` is the profile the caller reached the
console through, as the forwarded identity names it. `wait` is capped at 60 seconds,
as the Hub caps it; absent, it is 0.

### Calls To The Hub

The route builder declares `calls_hub`, so the server registers the token exchange
grant without declaring uses of any other server. Each tool takes the bearer
`ctx.client()?.hub_bearer()` returns: the caller's forwarded token exchanged at the
Hub's token endpoint for the caller's profile, naming no permissions, cached for the
request. The Hub admits it as the caller and decides each route by the caller's own
grants: a selection is the caller's own, an instance's status and a watch need the
caller's grant on the repository. A Hub refusal, such as 403 without a grant or 404
without an instance, is the tool's error result, naming what was refused, the HTTP
status and the Hub's RFC 9457 title and detail. Path segments are percent-encoded
one by one.

`InstanceStatus` follows the Hub's answer and reads only the fields it names; a phase
or stage it does not know fails the call with the Hub's value.

## Architecture

### Library Features

| Feature | Holds | Depends on |
|---|---|---|
| `contract` | `ConsolePermission`, `ConsoleScope`, `ConsoleProvider` and the tools' requests and results | `veoveo-types`, the SDK's `contract` feature, Serde and Schemars |
| `server` (default) | The hosted server and the binary | The SDK's `server` feature, core's store, reqwest and rmcp |

### Modules

| Module | Responsibility |
|---|---|
| `contract` | The public types a consumer compiles against |
| `mcp` | The typed ready routes, checked setup, registration declaration and the Hub's routes (`mcp::hub`) |
| `server` | Configuration, registration with the Hub, the database connection, the process instance and serving |

### Startup

The server builds its registration declaration from the public base URL and checks the
MCP setup before it contacts anything. It registers with the Hub, which issues a
database login for the `console` schema and the trust for forwarded tokens. With that
login it holds a process instance and serves. Serving ends on SIGTERM, on Ctrl-C or
when the instance loses its lock. Native saved registration remains for resume.

## Persistence

None. The server keeps no tables. Its database connection holds the kernel process
instance whose liveness the Hub reads as the server's health.
